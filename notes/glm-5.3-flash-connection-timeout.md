# GLM-5.3-Flash: six-minute disconnect investigation

Investigation after the MessagePack image-memory trial and OpenCode service
upgrade, 2026-10-03. No deployment or service settings changed during diagnosis.

**Follow-up:** the operator applied the recommended service environment change.
Verified OpenCode 2.0.22, new PID 148637, with
`BUN_CONFIG_HTTP_IDLE_TIMEOUT=1200` in `/proc/148637/environ`; rechecked during
the later performance research. Operator then reported several hours of
screenshot-driven work without crash or timeout. The disk provider configuration
still contains `options.headerTimeout=1200000`. The initial post-restart live
provider-API lookup returned 404, so it did not independently re-confirm provider
resolution at that moment. Sections below retain the diagnosis-time evidence.

## Independent lower-level timeout in embedded Bun

Ran the installed OpenCode executable in its embedded runtime mode:

```text
BUN_BE_BUN=1 /home/otto/.opencode/bin/opencode --version
1.4.2
```

This does not change or restart the service. It allows the diagnostic to use
the same executable's HTTP implementation rather than a separately installed Bun.
Diagnostic `Bun.revision` is `744846f844374847c902b5e7fd59b4342a51ef99`, exactly
matching GitHub's `bun-v1.4.2` commit, so the source links below match the executable.

Pinned source evidence:

- [Bun 1.4.2 `src/http/lib.rs:286–325`](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/http/lib.rs#L286-L325)
  defines a **300-second default socket timeout**, separately overridable by
  `BUN_CONFIG_HTTP_IDLE_TIMEOUT`. The header phase uses an absolute deadline;
  body reads reset it. Timer normalization pads the long wheel by a minute:
  `(ceil(seconds / 60) + 1) * 60`, explaining approximately six-minute behavior.
- [Bun `HTTPThread.rs:1172–1178`](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/http/HTTPThread.rs#L1172-L1178)
  reads that environment variable and defaults to 300. Units are **seconds**.
- [Bun `fetch.rs:741–775`](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/runtime/webcore/fetch.rs#L741-L775)
  supports a per-request `timeout: false` or numeric timeout override. This is
  a runtime fetch option, not OpenCode's provider JSON `headerTimeout` setting.
- [OpenCode 2.0.22 platform layer](https://github.com/anomalyco/opencode/blob/v2.0.22/packages/util/src/effect/app-node-platform.ts)
  uses `FetchHttpClient.layer`.
- [Effect 4.0.0-rc.112 fetch client](https://unpkg.com/effect@4.0.0-rc.112/src/unstable/http/FetchHttpClient.ts)
  defaults to `globalThis.fetch`, passing method, headers, body and abort signal.
- [OpenCode HTTP transport](https://github.com/anomalyco/opencode/blob/v2.0.22/packages/ai/src/route/transport/http.ts)
  enforces `headerTimeout` via an Effect timer around the HTTP operation. Raising
  that timer does not itself override Bun's native socket deadline.

The service upgrade made OpenCode's application-level timeout implementation
available, but did not establish that all lower-level deadlines were extended.
The generic `provider.transport` retry differs from the application's explicit
`Timed out waiting for response headers` message.

## Local isolation experiment

Diagnostic: `/tmp/opencode/glm53_timeout_isolation.py`.

A Python server bound only to local loopback waits **400 seconds** before sending
HTTP headers. Parallel clients use the installed OpenCode executable as Bun:
default fetch, `timeout:false`, `keepalive:false`, and a Python control. A
`Bun.FetchSession` alternative is also checked but that API is unavailable in this
embedded runtime. All Bun clients have a separate 450-second diagnostic abort
deadline. No model requests, NIM, Tailscale or remote network are involved.

A separate run tests `BUN_CONFIG_HTTP_IDLE_TIMEOUT=1200` only in its diagnostic
child process against another 400-second local wait. The live service environment
remains unchanged. **This control passed: HTTP 200 with the expected response at
400.002 seconds.** Thus the environment workaround removes the reproduced
six-minute cutoff in the same installed runtime. It does not itself constitute
a completed 20-minute wait or a real OpenCode/model end-to-end qualification.

**Measured initial isolation result:**

| Client | Outcome | Elapsed |
| --- | --- | ---: |
| Installed Bun, default fetch | `TimeoutError: The operation timed out.` (numeric code 23) | 360.311 s |
| Installed Bun, `keepalive:false` | Same timeout | 360.305 s |
| Installed Bun, `timeout:false` | HTTP 200, expected response body | 400.002 s |
| Python urllib control | HTTP 200, expected response body | 400.010 s |
| Installed Bun, `BUN_CONFIG_HTTP_IDLE_TIMEOUT=1200` | HTTP 200, expected response body | 400.002 s |

The local server observed connection resets on the default/keepalive-false
requests when attempting their 400-second responses. This reproduces the observed
six-minute cutoff without NVIDIA, Tailscale, model execution or GPU pressure.
Disabling connection reuse alone does not disable this native request timeout.

Error-display caveat: OpenCode's `executor.ts` schema expects an optional string
`code`, while this Bun `TimeoutError` supplies numeric code 23. That mismatch is
a source-level explanation for falling back to Effect's generic transport-error
message instead of exposing the native timeout text; it has not been separately
reproduced through the complete OpenCode error-mapping stack.

Artifacts: `/tmp/opencode/glm53-timeout-isolation-run.log` and
`/tmp/opencode/glm53-timeout-env-control.log`; per-run artifact directories are
named in those logs.

## Measured runtime correction, pending service-change approval

Persist the native runtime timeout at 1,200 **seconds**, retaining the provider's
1,200,000 **millisecond** header limit:

```sh
opencode service set env BUN_CONFIG_HTTP_IDLE_TIMEOUT 1200
opencode service start
```

The documented `service set env` command stops the shared service; `start`
launches it with the new environment. This can interrupt active sessions, so it
is not executed during this read-only diagnosis. Verify the new process's actual
environment and a long-wait provider request afterward. This runtime-wide setting
affects Bun fetch operations across providers; OpenCode's own provider timeout
limits continue to apply.

Reference: [OpenCode V2 managed-service environment configuration](https://opencode.ai/v2/docs/network/#service).
